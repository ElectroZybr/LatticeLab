# Антипаттерны

Чего не делать в LatticeLab: что плохо, почему и как правильно. Правила целиком — в
[Rules.md](Rules.md).

## Дублировать механизмы Lattice

Композицию, выбор и состав дерева решает только Lattice. Своя версия рядом — вторая система,
которая расходится с деревом.

### Своя композиция

**Плохо:** фабрика, реестр или «менеджер», который сам создаёт дочерние объекты, держит их в
контейнере и решает, что собрать; `if`/`switch` по режиму внутри объекта.

**Почему:** этих объектов нет в дереве — их не видно в CLI, у них нет параметров, владения,
зависимостей и lifecycle; заменить реализацию без пересборки кода нельзя.

**Правильно:** объекты создаются только в `compose.cpp` (и функциях вариантов слота). Вариант
реализации — `addSlot<API>().choice(...)`.

### Свой Focus

**Плохо:** объект сам выбирает «текущий / активный / целевой» объект (активный контроллер,
цель ввода, выбранный вьюпорт) или ведёт таблицу «объект → объект».

**Почему:** выбор живёт в двух местах и расходится; Context о нём не знает.

**Правильно:** `Focus<T>` / Context. Поле с таким значением допустимо, только если его
присваивает `configure` из Context (`ActionRouter::setTarget`, `Viewport::controller`).
Исключение — позиция навигации терминала CLI (`Terminal::current_`, аналог `cwd`).

### Ручной список детей

**Плохо:** собирать вектор детей в композиции вручную; объект ведёт свой список
(`add`/`remove`, регистрация колбеками).

**Почему:** список расходится с деревом при добавлении и удалении узлов.

**Правильно:** набор приходит из запроса дерева (`children<T>()`, `collect<T>()`) в
`configure`. Добавить объект в набор — добавить узел.

## Знание о Lattice в реализации

**Плохо:** реализация хранит builders, `NodeId`, `Ref`, наследуется от базовых классов Lattice.

**Почему:** её нельзя использовать и тестировать без runtime; сохранённый builder после
композиции недействителен.

**Правильно:** обычный класс с зависимостями в конструкторе; всё о Lattice — в `compose.cpp`.

## Терять зависимость

**Плохо:** `root.emplace<Consumer>("c", *device)` или `device.get()`.

**Почему:** разыменование теряет идентичность узла — зависимость не записывается, и удаление
поставщика не завершит потребителя.

**Правильно:** передавать сам handle: `root.emplace<Consumer>("c", device)` или `device.ref()`.

## Молча выбирать первого

**Плохо:** при нескольких кандидатах взять первый попавшийся.

**Почему:** результат зависит от порядка загрузки, ошибка конфигурации прячется.

**Правильно:** неоднозначность — явная ошибка со списком кандидатов; выбор — `focus`.

## Параллельная модель владения

**Плохо:** `std::shared_ptr` для объектов, которыми владеет дерево.

**Почему:** две системы владения: объект переживает свою ветку, retire не освобождает его.

**Правильно:** владеет дерево (`emplace`, общий ресурс — `emplaceShared` + `mount`);
`shared_ptr` — только если его требует внешний API.

## Узлы на всё подряд

**Плохо:** GPU-буфер, шейдер, surface, layout — отдельные узлы дерева.

**Почему:** дерево засоряется тем, чем никто не управляет; ресурсы живут дольше владельца.

**Правильно:** узел — то, чем управляют через дерево (добавить, настроить, удалить): вьюпорт,
камера, объект сцены, общие данные. Вспомогательные объекты — RAII-члены владельцев.

## Чужой поток в чужом состоянии

**Плохо:** читать или менять состояние сервиса (частицы, параметры симуляции) из host-потока
напрямую; мьютекс на каждое поле.

**Почему:** гонки и наполовину обновлённое состояние; мьютексы на поля не дают согласованности
между полями.

**Правильно:** только командами очереди потока-владельца (`executeOn`, копии для рендера —
команды); блокировки — в очереди и в сеттерах наборов из `configure`.

## Ждать в runtime

**Плохо:** блокировать `maintain` ожиданием готовности (`while (!ready) sleep`).

**Почему:** host-поток обслуживает всё дерево — встанет окно, CLI, пересборка.

**Правильно:** `readyToDestroy`, `onMaintain`, отложенные копии: проверять готовность на
следующем `maintain`, а не ждать.

## Границы модулей

**Плохо:** библиотека `libs/` зависит от пакета; симуляция знает о рендере или WGPU; рендер
знает о ClassicMD.

**Почему:** ломается выборочная сборка; домены сцепляются, и один нельзя заменить без другого.

**Правильно:** общий код — библиотека; симуляция публикует контракт (`ParticleSystemAPI`), рендер
делает копии сам и знает колонки, а не модели.

## Код под формат

**Плохо:** читать YAML или TOML напрямую в предметном коде.

**Почему:** новый формат требует правки всех потребителей.

**Правильно:** документ (`Lattice::Value`) через IO; новый формат — новый парсер.

## Шейдер строкой или по пути

**Плохо:** WGSL в строковом литерале C++ или чтение файла шейдера по пути от рабочего каталога.

**Почему:** строку не проверить и не подсветить; путь ломается при запуске из другой папки;
константы шейдера расходятся с C++ молча.

**Правильно:** `.wgsl` рядом с кодом, встраивание через `utils.bin2c`, `static_assert` на
константы через `Wgpu::shaderConstant`.

## Слои совместимости

**Плохо:** оставлять старый путь рядом с новым «на всякий случай».

**Почему:** два пути расходятся, и непонятно, какой настоящий.

**Правильно:** удалять устаревшее; история — в git.

## Производительность на глаз

**Плохо:** «вроде стало быстрее» после запуска приложения.

**Почему:** зависит от сцены, окна и случая; регрессию не увидеть.

**Правильно:** бенч рядом с кодом и прогон через `lbm` с сохранением истории
([Build.md](Build.md#бенчи)).
