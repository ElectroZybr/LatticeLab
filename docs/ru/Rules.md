# Правила разработки

Как писать код в LatticeLab. Устройство проекта — в [архитектуре](articles/Architecture.md),
чего не делать — в [антипаттернах](Antipatterns.md), механизмы Lattice — в его
[документации](README.md#ядро-lattice).

## Сначала — где это лежит

Перед новым модулем реши, где лежит каждая его часть и от чего она зависит. Границы:

| Где | Что | Зависит от |
| --- | --- | --- |
| `libs/<name>/` | модели, алгоритмы, структуры данных, бэкенды | другие `libs/`, сторонние библиотеки; из Lattice — только заголовочные `Table`, `Exception`, `PipelineAPI`, `NamedRegistry` и `lattice-logger` |
| `packages/<name>/` | композиция ветки (`compose.cpp`) и классы, нужные только ей | `libs/`, другие пакеты, runtime Lattice |
| `../Lattice` | ядро | — (не меняется из LatticeLab) |

- Библиотеки не зависят от пакетов: иначе ломается выборочная сборка. Общий код пакета и
  библиотеки — библиотека.
- Код, которому нужен runtime (`ExportsView`, `TreeView`, `ActionContext`), живёт в
  `packages/`, даже без своей ветки: модуль без `compose.cpp` размещает пакет, в контексте
  которого он имеет смысл (`Actions` — Shell, `Serialization` — StdIo).
- Критерий пакета — собирает ли код свою часть дерева (даже если её вкладывает другой пакет
  через `root.compose(...)`, как Graphics в Shell).
- GPU-вычисления — `libs/wgpu` (без рендера); рендерные примитивы (`Surface`, `RenderPass`,
  `RenderPipeline`) — `Graphics.core`; пакет `WGPU` только публикует общий `Wgpu::Device`.
- Симуляция не знает о рендере и не зависит от GPU: читатели получают данные через её контракт
  и копии командами её очереди.

## Реализация

- Обычные классы: зависимости — аргументами конструктора (`T&`, `T*`, `std::vector<T*>`,
  значения), контракты — полиморфные интерфейсы с виртуальным деструктором.
- Никаких builders, `NodeId`, handles и базовых классов Lattice внутри. Композицию, выбор и
  состав дерева решает только Lattice.
- Ошибки — `Lattice::Exception<Owner>`; в файле `using Error = Lattice::Exception<Owner>;`.
  Отдельных классов ошибок нет; ловить общим `Lattice::ExceptionBase`.
- Комментарий — там, где без него непонятно: неочевидное решение, договорённость с шейдером
  или раскладкой. Код не пересказывать.

## Композиция

`compose.cpp` пакета — единственное место, знающее о Lattice. API композиции и правила —
в [композиции Lattice](../../../Lattice/docs/ru/articles/Composition.md). Главное:

- Сначала поставщики, затем потребители; передавай в `emplace` сам handle, а не `*handle`
  или `handle.get()` — иначе зависимость не записывается.
- Регистрируются только конкретный тип и явно указанные API.
- Наборы детей и выбор (`children`, `collect`, `focus`) в `configure`, а не вручную.
- Объект, который читают из другого потока, получает набор сеттером с синхронизацией.
- Метаданные пакета — `constinit` в `lattice_package`; blueprint пакета называется по `id`.

## Модуль

```text
packages/stdio/
├── stdio/         весь код модуля: .hpp и .cpp вместе
├── compose.cpp    только у пакета
├── tests/         тесты реализации без runtime, одна цель <Name>.tests
├── bench/         бенчи горячих путей, одна цель <Name>.bench
├── README.md
└── xmake.lua
```

- Имена каталогов — в нижнем регистре (`packages/classicmd/classicmd`,
  `libs/boundaries/boundariescpu`); регистр имён C++-типов, файлов и целей сборки сохраняется.
- Маленький модуль — один заголовок (`inline`). Пара `.hpp/.cpp` — когда есть причина:
  большой объём, тяжёлые или сторонние зависимости, которые не должны видеть потребители,
  встроенные данные, состояние в единице трансляции.
- Подключение: внутри модуля — `#include "File.hpp"`; из `compose.cpp`, тестов и других
  модулей — `#include <module/File.hpp>`. Путь поиска — корень модуля, чужой модуль виден
  только через `add_deps`.
- Цели: `<Name>.core` (реализация, без runtime), `<Name>` (пакет: `compose.cpp`),
  `<Name>.tests`, `<Name>.bench`; у библиотеки — `<Name>` и `<Name>.tests`.

## Шейдеры

- Файлы `.wgsl` рядом с кодом, не строки в C++. Встраиваются при сборке
  (`add_rules("utils.bin2c", {extensions = {".wgsl"}})`, `#include "File.wgsl.h"`) — без
  зависимости от рабочего каталога.
- Шейдер самодостаточен: константы, повторяющие C++ (коды операций, размеры), записаны в нём;
  совпадение проверяет `static_assert` через `Wgpu::shaderConstant` — расхождение ломает сборку.
- Разные режимы отрисовки — разные реализации (варианты слота), а не `if` внутри объекта.

## Модель и бэкенды

Алгоритм с несколькими исполнениями — `libs/<name>/` с моделью и бэкендами рядом (эталон —
`libs/boundaries`, раскладка — в [архитектуре](articles/Architecture.md#модель-и-бэкенды)).

- **Модель:** параметры и таблицы — POD-записи с фиксированной раскладкой (`static_assert`
  размеров), бэкенд копирует их на устройство без перепаковки; проверки конфигурации общие
  для всех бэкендов. Модель не знает об устройстве и потоках.
- **Бэкенд:** только исполнение модели; имена ролей с префиксом устройства (`Cpu::Walls`,
  `Wgpu::GpuWalls`). GPU-бэкенд записывает проходы в чужой `Wgpu::CommandList` и не делает
  `submit`; ошибки шейдера и pipeline — исключение при создании.
- **Новая операция:** запись модели + функция в каждом бэкенде + константа в шейдере со
  `static_assert` + строка в тесте эквивалентности. **Новый бэкенд:** папка и цель, тесты
  эквивалентности против CPU, бенчи рядом; модель не меняется.

### Ядро на раздел

Чтобы алгоритм можно было раздать по устройствам и узлам:

- ядро обрабатывает раздел строк `[begin, end)` и не держит глобального изменяемого состояния;
- входные и выходные колонки объявлены явно (раскладка);
- соседи — только через структуру соседей с гало;
- редукции (min/max/sum, счётчики) объявлены явно.

## Потоки

- Дерево, Context, регистрация экспортов, `configure`, рендер и графические ресурсы — только
  на host-потоке.
- Сервис со своим потоком — единственный владелец своего состояния; снаружи — только командами
  его очереди. Экспорты такого объекта привязываются к очереди (`obj.executeOn(queue)`) до
  `param`/`action`.
- Блокировки — внутри очереди и в сеттерах наборов из `configure`, а не на каждом поле.

## Тесты

- Тесты модуля — `tests/`, одна цель `<Name>.tests`, без runtime: модель, бэкенды и их
  эквивалентность вместе.
- GPU-проверки пропускаются без адаптера; после них — ни одной ошибки валидации и ни одного
  живого ресурса устройства.

## Бенчи

Для кода, где важна производительность, бенчи пишутся сразу с реализацией; размеры — от тысяч
до миллиона элементов. Инструмент — [BmRunner](../../../Lattice/docs/ru/articles/BmRunner.md).

- Реализации одной работы — `BENCH_WORK` и `BENCH_IMPLEMENTATION` (имя = имя варианта слота);
  каждая сверяется с эталоном до замеров. Потоки — ось `Tasks::Workers`, не отдельная
  реализация.
- Функция бенча размечает фазы (`Prepare`, `Transfer`, `Issue`, `Execute`, `Complete`); время
  GPU — `Wgpu::Timer` и `trace.deferIntervals(timer)`.
- GPU: после загрузки — `device().flush()`; в `Resident` состояние сбрасывается копией на GPU;
  дорогая фикстура — `static constexpr bool Reuse = true`.
- Производительность меряется бенчем, а не «на глаз».

## Данные

- Не привязывай код к формату: работай с документом (`Lattice::Value`) через IO. Новый формат —
  новый парсер в композиции IO.
- Конфигурация запуска — `lattice.toml` (`[Startup]`), значения runtime — `config/`,
  пользовательские переопределения — `user/`.

## Документация и планы

- Документация — для человека и агента одновременно: понятна с нуля, без истории проекта.
- Механизмы Lattice описываются только в его документации; здесь — ссылки.
- Планы: [plans/README.md](plans/README.md) — крупные блоки с чекбоксами; у каждого блока
  свой файл в `plans/`: `# Название`, 1–3 строки цели со ссылками, этапы с чекбоксами.
  Пункты отмечаются в файле блока; закрытый блок отмечается и переносится в «Готово» одной
  строкой итога.
- Проект подсистемы (устройство, решения, ограничения) — статья в `articles/`.

## Предпочитай

- обычный, независимый от фреймворка код реализации; всё знание о Lattice — в `compose.cpp`;
- явные связи и видимое владение; зависимости через конструктор;
- детерминированную ошибку при неоднозначности;
- маленькие ортогональные примитивы ядра, предметное поведение — в пакетах;
- удаление устаревших путей вместо слоёв совместимости.
