# Serialization

Модуль применяет частичную конфигурацию дерева Lattice и сохраняет пользовательский
слой явных переопределений параметров по структуре дерева. Реализация — `Serializer`
(`Serialization.core`); своей ветки нет: его размещает пакет StdIo рядом с IO
(`StdIo/Serializer:config`) и экспортирует `load`/`save` на корне своей ветки.
Файлы читает и записывает обычный `IOSubsystem` из StdIo через `Document` и
`ParserAPI`; сериализатор не открывает файлы самостоятельно.

Композиция StdIo передаёт свой IO обычной C++ ссылкой в конструктор Serializer. Его
runtime-зависимость оправдана назначением: это инфраструктурный адаптер Builder/Exports,
а не предметный компонент. Он не хранит NodeBuild.

Действия регистрируются через `serializer.action(...)`. Корень композиции
перенаправляет startup/CLI-вызовы через Exports, чтобы удалённый сервис не оставлял
callback с висячим указателем. Удаление IO или парсера, от которого он зависит,
завершает и сериализатор. Каждая ветка StdIo получает свой сериализатор над своим IO. См. [структуру StdIo](../StdIo/README.md).

## Внешний Lattice

LatticeLab использует пакет `lattice` из внешнего проекта, по умолчанию `../Lattice`.
Xmake устанавливает библиотеку, публичные заголовки и её зависимости в package cache.
Встроенная копия ядра не собирается. Путь можно задать опцией `lattice_source`.
Существующие plugin targets получают внешний пакет через интерфейсный target `Lattice`.

Для сборки сериализатора без графических плагинов:

```sh
xmake f -y --lattice_source=../Lattice --lab_packages=StdIo,Serialization
xmake build StdIo.tests
xmake run StdIo.tests
xmake build Serialization.tests
xmake run Serialization.tests
xmake build LatticeLab
```

Пустое значение `lab_packages` включает все директории плагинов. Эта настройка
выбирает цели сборки; остальные плагины не переносятся на новый API автоматически.

## Конфигурация

```yaml
Lattice:
  CLI:
    theme.err: "#336688"
  ClassicMD:Universe1:
    integrator:
      dt: 0.125
```

Каждый вложенный ключ — непосредственный ребёнок дерева или экспортированный
параметр текущего объекта. `children`, `blueprint`, `name` и `params` не являются
служебными полями формата. Ветка и её параметры записываются прямо по иерархии.

- `cli` — имя существующего дочернего объекта. Его тип уже определён композицией.
- `CLI` — безымянная композиция пакета. Точное имя blueprint имеет приоритет над
  короткими именами C++ классов, например `Console::CLI`.
- `ClassicMD:Universe1` — тип композиции и имя экземпляра. Такой ключ позволяет
  восстановить отсутствующую ветку через Builder. Для обычных объектов сохраняется
  только имя; для границ композиции сохраняется тип, необходимый для пересоздания.
- При неоднозначных именах детей используется полное `Тип:имя`; `::` внутри C++
  namespace остаётся частью типа. Для структурной ветки без типа доступно `:имя`.
- Экспортированный параметр распознаётся прежде ребёнка, даже если его значение —
  словарь. Если ребёнок называется так же, обращение к нему требует `Тип:имя`.
- Неуказанные параметры и ветки остаются как есть. Actions не являются параметрами.
  NodeId, указатели и память C++ объектов не сохраняются.
- Неизвестные ключи, неверные типы, неоднозначные пути и retiring-ветки дают ошибку.
  При retiring нужно дождаться обслуживания runtime и повторить загрузку.

Словари не задают порядок зависимостей: необходимые общие поставщики должны быть
собраны до загрузки слоя, например через `[Startup]`. Параметры узла применяются
до его дочерних конфигураций; дочерние ключи обходятся в алфавитном порядке.

Параметры применяются после создания объектов. Целые числа и дробные числа
преобразуются, если это не теряет дробную часть при записи в целое. Векторы glm
читаются из массивов нужного размера. Строки, bool, массивы и объекты используют
существующий `Value`/`ParamAdapter` Lattice.

Загрузка выполняется последовательно, не является общей транзакцией: при ошибке
ранние успешно созданные ветки или записанные параметры могут остаться. Неудачная
сборка отдельной ветки откатывается существующим Builder. Замена реализаций Slot
и удаление отсутствующих в файле веток этим форматом не запрашиваются.

## Загрузка и сохранение

В `lattice.toml` Serialization включён после StdIo. Runtime вызывает его
действие `load` при загрузке startup-данных, до запуска сервисов.
По умолчанию читается `User/runtime.yaml`. Это пользовательский слой, исключённый
из Git. При первом запуске отсутствие файла означает пустой слой; `save` создаёт
папку `User` и файл. `Config/` автоматически не перезаписывается.

Композиция экспортирует `load([path])` и `save([path])` на своём корне. Их можно
вызывать через существующий Exports API/CLI. Без аргумента:

- первый `load` читает `User/runtime.yaml`, следующие — текущий файл;
- `save` обновляет текущий файл; до первого `load`/`save` используется `User/runtime.yaml`.

`save(path)` сохраняет слой по новому пути и делает его текущим файлом. Предварительный
`load` не обязателен. Остальные секции последнего успешно загруженного документа
сохраняются; секция `Lattice` собирается заново по живому дереву.

Пользовательский слой хранит **явно заданные значения**, без снимка исходного состояния:

- `load` применяет параметры через `Exports::set` и добавляет их в слой;
- CLI-присваивания и инспекторы используют `ExportsView::set` (или `Exports::set`);
- явная запись значения, совпадающего с исходным, тоже считается переопределением;
- обычная запись в C++ поле и raw-setter `ResolvedExport::set` не меняют слой.
  Этот setter остаётся для временного ввода, например движения камеры;
- `save` записывает значения слоя, а не перечитывает поля: последующие внутренние
  изменения объекта не меняют пользовательские настройки;
- строки, массивы и объекты копируются глубоко, поэтому слой не разделяет их
  изменяемое содержимое с объектами приложения.

`reset <параметр>` (в том числе `reset #<exportId>`) в CLI вызывает
`ExportsView::reset` и удаляет переопределение. **Текущее поле не изменяется**:
исходных значений в памяти нет. При новой сборке ветки без этого переопределения
применится значение композиции. Reset не является восстановлением состояния объекта.

Сохраняются все переопределения в поддереве, включая параметры и ветки, которых не
было во входном файле. Цепочка родителей повторяет иерархию runtime; ключи с типом
различают безымянные стартовые ветки разных пакетов. Загруженные композиции
сохраняются как объявления, даже без параметров. Ветки
без переопределений и объявлений опускаются. Retiring/удалённые ветки не записываются;
их параметры забываются при снятии экспортов. Новый экземпляр не наследует отметки
удалённого, даже при повторном использовании NodeId.

Повторный `load` накладывает перечисленные значения поверх текущего слоя; отсутствие
параметра в новом документе не означает reset. Загрузка остаётся последовательной:
при ошибке уже применённые значения остаются и в объекте, и в пользовательском слое.
При ошибке записи текущий путь и сохранённый документ не меняются; переопределения
остаются в памяти для повторного сохранения.

Стандартный формат — YAML (`.yaml` и `.yml`). Parser и writer находятся в StdIo
и используют [yaml-cpp](https://github.com/jbeder/yaml-cpp). TOML остаётся доступен
при явном выборе файла с расширением `.toml`.

YAML writer форматирует весь документ, записывает временный файл рядом и
переименовывает его после успешной записи. Строки записываются в кавычках,
чтобы `"true"`, `"123"` и `"null"` сохраняли тип. Словари выводятся с сортировкой
ключей; обычные ключи остаются без кавычек, специальные и зарезервированные
YAML-ключи экранируются. Порядок списков сохраняется. Комментарии и исходное форматирование
не сохраняются. YAML null отклоняется: у `Lattice::Value` нет такого типа.
Повторные ключи, циклические aliases и несколько YAML-документов в одном файле
также отклоняются; корень должен быть словарём. Ошибки чтения/разбора больше не превращаются
в пустой документ. Парсеры без writer (например TSV) явно отклоняют запись.

## Проверки

`tests/Serialization_tests.cpp` загружает настоящие пакеты StdIo и Serialization.
Двенадцать групп сценариев проверяют загрузку/round-trip, новые явные переопределения,
игнорирование прямых записей, глубокую изоляцию вложенных значений, reset, сохранение
до load, retirement и повторное использование узлов, безымянные ветки разных типов,
YAML/TOML, совпадающие имена детей и параметров, ошибки IO, зависимости и выбор общего IO.

Команда `config` доступна из любого узла CLI и показывает текущий файл и число
переопределений. Этот статус также печатается при запуске CLI. Значения можно
проверить в соответствующем узле: например `cd /CLI`, затем `theme.err`.
