# Serialization

Плагин применяет частичную конфигурацию дерева Lattice и сохраняет только
указанные в ней экспортированные параметры. Реализация находится в `Serializer`,
сборка и экспорт действий — в одном `compose.cpp` с точкой входа `compose`.
Файлы читает и записывает обычный `IOSubsystem` из StdIo через `Document` и
`ParserAPI`; сериализатор не открывает файлы самостоятельно.

Композиция получает общий IO через `root.mount<IOSubsystem>()` и передаёт обычную
C++ ссылку в конструктор Serializer. Его runtime-зависимость оправдана назначением:
это инфраструктурный адаптер Builder/Exports, а не предметный компонент. Он не
наследуется от Component и не хранит NodeBuild. `Serialization.core` содержит
реализацию; target `Serialization` — только файл композиции.

Действия регистрируются через `serializer.action(...)`. Корень композиции
перенаправляет startup/CLI-вызовы через Exports, чтобы удалённый сервис не оставлял
callback с висячим указателем. Mount связывает lifetime всей ветки с общим IO.
Несколько IO-кандидатов требуют явного Focus; уже созданный Serializer сохраняет
свой снимок зависимости. См. [структуру StdIo](../StdIo/README.md).

## Внешний Lattice

LatticeLab использует пакет `lattice` из внешнего проекта, по умолчанию `../Lattice`.
Xmake устанавливает библиотеку, публичные заголовки и её зависимости в package cache.
Встроенная копия ядра не собирается. Путь можно задать опцией `lattice_source`.
Существующие plugin targets получают внешний пакет через интерфейсный target `Lattice`.

Для сборки сериализатора без графических плагинов:

```sh
xmake f -y --lattice_source=../Lattice --lab_plugins=StdIo,Serialization
xmake build StdIo.tests
xmake run StdIo.tests
xmake build Serialization.tests
xmake run Serialization.tests
xmake build LatticeLab
```

Пустое значение `lab_plugins` включает все директории плагинов. Эта настройка
выбирает цели сборки; остальные плагины не переносятся на новый API автоматически.

## Конфигурация

```yaml
Lattice:
  children:
    - name: simulation
      blueprint: MySimulation
      children:
        - name: integrator
          params:
            dt: 0.125
            iterations: 100
```

Пути отсчитываются от корня приложения. `children` — упорядоченный список:
поставщика можно объявить раньше зависимой ветки. Имена относятся к непосредственным
детям. Композиция `MySimulation` может уже создать `integrator`: тогда он используется
повторно, без отдельного blueprint в конфиге.

- Нет ветки — нужен зарегистрированный `blueprint`; она создаётся через `Builder`.
- Ветка существует — применяются только перечисленные параметры. Повторная загрузка
  не дублирует объекты. Указанный blueprint должен совпадать с существующей веткой.
- Неуказанные параметры и ветки остаются как есть. Actions не являются параметрами.
- NodeId, указатели и память C++ объектов не сохраняются.
- Неизвестные поля, типы, параметры, неоднозначные имена и retiring-ветки дают ошибку.
  При retiring нужно дождаться обслуживания runtime и повторить загрузку.

Параметры применяются после создания объектов. Целые числа и дробные числа
преобразуются, если это не теряет дробную часть при записи в целое. Векторы glm
читаются из массивов нужного размера. Строки, bool, массивы и объекты используют
существующий `Value`/`ParamAdapter` Lattice.

Загрузка выполняется последовательно, не является общей транзакцией: при ошибке
ранние успешно созданные ветки или записанные параметры могут остаться. Неудачная
сборка отдельной ветки откатывается существующим Builder. Замена реализаций Slot
и удаление отсутствующих в файле веток этим форматом не запрашиваются.

## Загрузка и сохранение

В `lattice.toml` Serialization включён после StdIo. Runtime вызывает его
действие `load` при загрузке startup-данных, до запуска сервисов.
По умолчанию читается `Config/runtime.yaml`; файл содержит пустой словарь `Lattice: {}`,
поэтому ничего не добавляет, пока в нём нет описаний веток и параметров.

Композиция экспортирует `load([path])` и `save([path])` на своём корне. Их можно
вызывать через существующий Exports API/CLI. Без аргумента:

- первый `load` читает `Config/runtime.yaml`, следующие — текущий файл;
- `save` обновляет текущий файл; до успешного `load` сохранение отклоняется.

`save(path)` сохраняет копию по новому пути и делает её текущим файлом. Сериализатор
хранит один текущий документ. При сохранении он обходит только его `params`, читает
актуальные значения Exports и сохраняет остальные секции документа. Новые runtime
параметры не попадают в файл автоматически. Если сохранённая ветка уже удалена,
выдаётся ошибка, без её восстановления и без изменения файла.

Стандартный формат — YAML (`.yaml` и `.yml`). Parser и writer находятся в StdIo
и используют [yaml-cpp](https://github.com/jbeder/yaml-cpp). TOML остаётся доступен
при явном выборе файла с расширением `.toml`.

YAML writer форматирует весь документ, записывает временный файл рядом и
переименовывает его после успешной записи. Строки записываются в кавычках,
чтобы `"true"`, `"123"` и `"null"` сохраняли тип. Словари выводятся с сортировкой
ключей; порядок списков сохраняется. Комментарии и исходное форматирование
не сохраняются. YAML null отклоняется: у `Lattice::Value` нет такого типа.
Повторные ключи, циклические aliases и несколько YAML-документов в одном файле
также отклоняются; корень должен быть словарём. Ошибки чтения/разбора больше не превращаются
в пустой документ. Парсеры без writer (например TSV) явно отклоняют запись.

## Проверки

`tests/Serialization_tests.cpp` загружает настоящие плагины StdIo и Serialization
и проверяет восемь групп сценариев: достройку/повторную загрузку/round-trip, типы и
неуказанные параметры, ошибки дерева и retirement, save-as и удалённые ветки,
ошибки парсинга/формата и сохранность файла при ошибке writer, YAML-типы,
кавычки, многострочные строки, aliases и поддержку `.yml`, зависимости и
retirement IO/Serializer, неоднозначность общего IO и явный Focus.
